## 一、先把数字对齐：没有「还有 500 个没翻」

你记的「1500 翻完了、还有 500 没翻」，是两个口径混在一起了。

### 全量候选 28,816 个的真实构成

| 状态 | 数量 | 含义 |
|---|---:|---|
| `no-quests` | 23,817 | **根本没有任务书**（纯模组包/资源包/光影包）。永远不会有产出，不是「没翻」 |
| 探测未完成 | 2,905 | 还没探测到任务书情况（缺 CF 元数据/包太大跳过） |
| `downloadable` | **1,579** | 已出独立汉化补丁 ← 这就是你说的「1500」 |
| `embedded` 未交付 | 427 | 内嵌布局、还没做的。**注意：内嵌不等于不可翻**（见下方更正） |
| `native-zh` | 49 | 作者本来就带中文 |
| `gap-uncovered` | 39 | 有英文源、本站没翻、社区（VM/CFPA）也没人翻 ← **真正的缺口** |

### 你看到「990 分片」的完成度

上一轮切给 5 台主机的任务是 **990 个**（每台 198 个），不是全量。

| | 数量 |
|---|---:|
| 分片合计 | 990 |
| **已入库** | **778** |
| 未入库 | 212 |

212 个未入库的构成（按数据集状态）：

| 状态 | 数量 | 说明 |
|---|---:|---|
| `embedded` | 191 | 内嵌布局；其中多数是翻译后发现「没有可译文本」被跳过（见更正） |
| `gap-uncovered` | 18 | 真的没翻 |
| `no-quests` | 2 | 探测后发现没任务书 |
| 不在候选库 | 1 | 已从榜单消失 |

**结论：真正「该翻还没翻」的只有 18 个**，不是 500 个。

### 更正：内嵌布局**不是**「不能翻」

我先前说「内嵌出不了独立补丁」是错的，数据打脸：

| layout=embedded | 数量 |
|---|---:|
| **已交付** | **1,121** |
| 未交付 | 427 |

抽检一个已交付的内嵌包 `prominence-2-hasturian-era`：它的产物就是 33 个
`config/ftbquests/quests/chapters/*.snbt` —— 把翻译后的章节文件原样替换进整合包即可生效。
这就是独立补丁，只是形态是「整章覆盖」而不是「语言文件」。

所以 191 个未入库的内嵌包，理由不是布局，而是翻译时判定 **「没有可译文本」**
（任务书里只有 `tasks`/`rewards`/`icon` 这类机械字段，没有标题/描述文本）。
这个判定对不对需要抽检——若误判，就是几百个包的增量。

## 二、CI 到底稳不稳：我做了 96 路实测

先纠正一个前提：**CI 从来没跑过 96 路**。

线上 `translate.yml` 调的是 `scripts/pipeline.mjs`，这条路径**没有 lanes 概念**，一个包翻完再翻下一个。所以之前那些「840s 超时」不是机器慢，是结构上必然——一个含 3000 条译文的大包，串行跑不完 840 秒。

主机上跑的 96 路是另一套代码（`translate-local.mjs --lanes`）。

### 实测（工作流 `spike-lanes`，同一个包 `skyt-2`，1256 条译文）

| 并发 | 耗时 | 峰值内存 | 结果 |
|---|---:|---:|---|
| 8 路 | **95 秒** | 34 MB | 成功，1249/1256 条，漏译 5 |
| **96 路** | **23 秒** | 44 MB | 成功，1247/1256 条，漏译 6 |

- 8 → 96 路换来 **4.1 倍**加速（不是线性，因为下载/解包/合并是固定开销）；
- **96 → 512 路：时间一模一样（23 秒），内存从 44MB 涨到 205MB**。
  说明 96 路已经撞到真正的瓶颈——**LLM 网关的并发上限 / 单请求延迟**，不是 CI 的机器。
  继续加路数只会烧内存，不会更快。**96 就是拐点。**
- **没有出现 504**，没有 OOM，GitHub 标准 runner（2 vCPU / 8G）扛得住；
- 关键前提：这两个包的基准源（`research/packs/<slug>.tar.gz`）**已经在仓库里**，所以 prepare 只花了 0.97 秒。**新包要现场下载 100~300MB，那才是真正的时间大头**，跟并发无关。

### 各工作流的历史成功率（最近 60 次）

| 工作流 | 成功 | 失败 | 成功率 | 失败原因 |
|---|---:|---:|---:|---|
| Deploy to Cloudflare | 33 | 1 | **97%** | 偶发 |
| farm-merge | 9 | 11 | **45%** | 全是夸克镜像 / 玩家请求两条旁路 job 把它拖红 |
| translate | 0 | 1 | 0%（只跑过 1 次） | 串行 840s 超时 + 免费层 504 |

### 结论：CI 不是「不稳定」，是「用错了地方」

- **它在行的**：干净的 Linux 环境、免费算力（公开仓库不计费）、定时触发、跑完就销毁。
  96 路实测 23 秒翻完 1256 条，这个数字比主机还好看（主机同样 35 秒，还是同一批机器跑别的活）。
- **它不在行的**：需要登录态/浏览器会话的（夸克 cookie 会过期）、单 job 6 小时上限、
  大磁盘任务（runner 只有 14G 盘，塞不下多个几百 MB 的整合包同时解包）、需要人盯的交互。

所以我的判断：**CI 完全能承担「玩家请求的翻译」，而且是最省事的**——提交量小（历史上 3 条）、
用 96 路每个包 20~30 秒、不占你的主机、你也不用开着电脑。真正的成本是「新包要下载」那 1~3 分钟。

但你之前说过「换到本机就是因为 CI 不稳」。现在实测数据不支持这个判断：
**不稳的是串行 pipeline + 免费层限流，不是 CI 本身。** 这条请你重新考虑。

## 三、方案：玩家提交 → 仓库清单 → 本机/CI 消费

### 3.1 身份与去重（解决 CF/Modrinth 重复发布）

你提到同一作者会往两个平台发同一个包，数据里确实存在：按「规范化标题」比对，
**494 组**在两个平台同名（`rlcraft` / `rl-craft`、`better-mc-forge-bmc4` 两侧都有等）。

三级身份：

| 层级 | 键 | 用途 |
|---|---|---|
| 平台内 | `platform + slug` | 唯一确定一个平台条目 |
| **跨平台实体** | `groupId`（新增 `research/pack-identity.json`） | 判重、判版本 |
| 玩家提交 | 规范化 URL → `platform + slug` → `groupId` | 入库 |

`pack-identity.json` 由脚本自动生成候选（同名组 494 个），只把**同名但其实是不同包**的歧义项交人工确认。
结构：

```json
{ "groups": [
  { "id": "better-mc-forge-bmc4", "title": "Better MC [FORGE] BMC4",
    "members": [ {"platform":"cf","slug":"better-mc-forge-bmc4"},
                 {"platform":"mr","slug":"better-mc-forge-bmc4"} ] }
] }
```

### 3.2 版本判定（按你说的「按我推荐的来」）

- **CurseForge**：比 `fileId`（每次发版必变，数字最可靠）；
- **Modrinth**：比 `fileName` 里的版本串（没有 fileId）；
- **跨平台实体**：取各成员里 `fileDate` 最新的那条作为实体当前版本；
  **任一成员出现新版本 → 视为需要重翻**（用那个新版本翻，因为内容可能不同）；
- **解析不出版本** → 一律**按「需要重翻」处理**（宁可多跑一次，不漏）。

这些字段仓库里已经有了：`research/source-versions.json` 的 `versions[slug] = {platform, fileId, fileName, fileDate}`，
以及 `patches/<slug>/.source.json`。

### 3.3 清单（放在仓库里）

`research/submissions.jsonl`，**append-only，一行一条**：

```json
{"id":"ciscos-fantasy-medieval-rpg-dragonfyre","url":"https://www.curseforge.com/minecraft/modpacks/...","platform":"cf","slug":"ciscos-...","groupId":"ciscos-...","versionAtSubmit":"fileId:5123456","requestedAt":"2026-10-23T06:22:36Z","requestedBy":"玩家","note":"Cisco's Fantasy Medieval RPG","status":"pending"}
```

- **任务单在仓库**（谁提交了什么、什么时候、版本多少）——可审计、可回滚、diff 干净；
- **状态仍在 KV**（页面展示用），本机跑完写回 KV；
- 仓库里只保留 `pending` 与最近 90 天的 `done/failed`，更早的归档到 `research/submissions-archive/`。

### 3.4 消费（先本机，手动）

```
npm run requests              # 拉清单 → 逐条判重/判版本 → 翻译 → 打包 → 回写状态 → 提交
npm run requests -- --dry-run # 只列出「哪些要跑、哪些跳过、为什么」
npm run requests -- --only=skyfactory-5
```

流程（每条）：

1. `GET /queue` 拿 KV 现状，与仓库清单取并集（防止 Worker 写失败时漏单）；
2. URL → platform + slug → groupId；查 `pack-identity.json` 归并到实体；
3. 比版本：一致 → 标记 `skipped(same-version)` 并回写「已有，版本 X」给玩家；
   不一致或库里没有 → 进入待跑；
4. `prepare-pack` → `translate-local --lanes 96` → `release` 打包；
5. `git commit` 单条提交（便于 revert 单包），`POST /status` 回写 KV；
6. 全部跑完再 `npm run publish`——**清单消费与发布解耦**，
   避免把「玩家提交」和「站点发布」绑在一次操作里（出错难定位）。

### 3.5 站点改动（小）

- 提交页已有的状态条继续用，只是状态来源从「管理区手动点」变成「清单被消费」；
- 新增一条提示：**「该整合包已在库中，当前版本 X」**——版本相同被跳过时告诉玩家原因，
  这是现在最缺的体验（玩家提交完没反应，以为提交失败）；
- 管理区的「翻译」按钮保留，作为强制重翻的逃生阀。

## 四、工作量与风险

| 项 | 内容 | 预估 |
|---|---|---|
| A | `pack-identity.json` 生成脚本 + 494 组自动归并 + 歧义清单 | 2~3 小时 |
| B | `scripts/requests.mjs`（拉队列、判重、判版本、调度、回写） | 4~6 小时 |
| C | Worker 小改：`/status` 增加「同版本跳过」状态；提交时返回 groupId/版本 | 1~2 小时 |
| D | 提交页提示文案 + 队列列表展示版本 | 1 小时 |
| E | 3 个 B 类包（`snbt-repair` 加两条窄规则） | 2~3 小时 |
| F | 发布自检（restore 后比对 snbt 数） | 1 小时 |

**风险点**

1. **跨平台归并会误判**：494 组里必然有同名不同包（比如都叫 "Skyblock"）。
   → 所以自动归并只做「同名且 slug 高度相似」；其余进 `needs-review` 清单，人工确认后才归并。
2. **版本号口径不一致**：CF 的 fileId 变、MR 的 version_number 变，两边节奏不同，
   可能出现「这边更新、那边旧」的来回重翻。
   → 加一条冷却：同一实体 7 天内最多触发 1 次自动重翻，之后需人工确认。
3. **玩家刷提交**：现在没有任何限流。
   → 按 IP + groupId 做 24 小时去重（Worker 侧，KV 有计数能力）。

## 五、请你拍板的三件事

1. **谁来跑**：本机手动（你已定）。但要不要**同时**保留「CI 96 路」作为第二条腿？
   我的建议是保留：玩家提交后你不用管，CI 会在 40 分钟内翻完；本机只在你想插队时用。
   （实测数据在上面，CI 这条路径是通的。）
2. **跨平台归并的严格度**：只自动归并「同名 + slug 相似度 ≥ 0.9」，其余人工？
   还是全部自动归并（省事但可能误判）？
3. **那 3 个 B 类包**：修解析器（推荐）/ 收窄闸门 / 放弃——你还没定。
