# 方向 A · 工具台 — 设计说明

产出：`design/A-工具台/index.html`（自包含，双击即可打开，无构建、无 CDN 依赖）。
数据：`design/demo-data.json` 的 22 条真实整合包数据，已内联进 HTML，字段未改写、未编造。

---

## 1. 先定人，再定界面（UX 研究员视角）

**被雇佣来完成的任务（JTBD）**
> 我在某个整合包里玩，任务书是英文看不懂 —— 我要在最短时间内确认「这个包有没有中文、我现在能不能拿到文件、拿到后放哪里」。

**主路径与可能卡住的地方**

| 步骤 | 玩家的问题 | 本设计给出的答案 |
|---|---|---|
| 1. 落到列表 | 「我玩的包有中文吗？」 | 状态徽章 + 顶部三状态计数条 |
| 2. 判断能不能下 | 「现在能下吗？」 | 计数条上「可下载」的数字直接回答；不能下就说明在排队 |
| 3. 进详情 | 「装哪里？」 | 下载面板与安装步骤同屏 |
| 4. 安装失败 | 「怎么没生效？」 | 安装说明里单独一块「常见错误」，覆盖放错目录这个头号投诉 |

**区分证据与假设**（本方向的核心判断）

- 证据（来自 BRIEF 与真实数据）：22 条数据里 **0 条可下载、7 条自带中文、15 条待翻译**；BRIEF 明确指出「安装说明不显眼」是本站投诉第一大来源、参考项目在手机端返工过一次。
- 假设 A：玩家第一眼要找的是「能下载的」。→ 设计含义：把三状态计数放在列表最顶部、点击即筛选。**验证方式最省成本**：埋点统计「可下载」筛选的点击率与详情页到达率。
- 假设 B：玩家不会读完安装步骤。→ 设计含义：在详情页用 4 步短句 + 独立「常见错误」块，且与下载按钮同屏。**验证方式**：对比「安装失败」反馈量。

## 2. 三状态是第一等公民

- 列表顶部固定展示 `0 可下载 / 7 自带中文 / 15 待翻译 / 22 全部`，数字来自真实数据实时计算，**没有任何状态被静默隐藏**。
- 状态一律用**带文字的徽章**表达，颜色只是辅助（`可下载` 绿、`自带中文` 蓝、`待翻译` 琥珀）。色觉障碍用户读文字即可，不依赖深浅。
- 点击计数即筛选，再点一次取消 —— 一个动作完成「筛出本站可下载的包」。
- 「自带中文」不是沉默地摆在列表里：详情页明确写「该整合包自带中文，请直接游玩，无需本站汉化包」，避免玩家白找。
- 「待翻译」的详情页给出「提交翻译请求」入口（原型内演示交互，文案中已注明未接后端），对应 BRIEF 里「提交请求 / 看进度」的可做动作。

## 3. 信息密度：让 22 行数据可比较

**列表结构（桌面）**：整合包 / 状态 / 分类 / 加载器 / MC 版本 / 中文-源文件 / 下载量。

- 数字列统一 `font-variant-numeric: tabular-nums` 并右对齐，下载量与文件比可以**纵向直接比较**。
- 文件覆盖统一成「中文 / 源文件」比值（如 `69 / 73`、`0 / 61`），三种状态用同一种口径，比「随包自带 69」这种混合说法更好比。
- 每行固定 50px 等高：分类与标题在桌面端单行省略（`text-overflow: ellipsis`），完整内容在详情页，**扫读时视线不会被换行打断**。实测所有行高 = 50px。
- 没有大 Hero、没有渐变、没有图标三连排。唯一的强调色 `--accent: #2563eb` 只用在可交互元素与当前筛选项上，层级靠字重与留白。

**为什么不用大卡片流**：一屏能看到的整合包数量直接决定「三秒内能不能判断」。卡片流一屏放 4–5 个，本方案一屏放 12+ 个。

## 4. 断点与移动端（响应式布局专家视角）

移动优先：默认样式即窄屏，向上增强。

| 断点 | 处理 |
|---|---|
| 默认（< 1024px） | 每行压成两行：`图标+名称 …… 下载量` / `状态 + 加载器 · 版本 · 文件比`，用间隔点分隔 |
| **≥ 1024px** | 展开为 7 列对齐数据表并显示列头（内容驱动：960–1023px 放不下 7 列） |
| **≥ 1200px**（指定桌面断点） | 加宽留白，仍保持 12+ 行可见 |
| **≤ 480px**（指定移动断点） | 收紧留白、元信息字号降到 12px、隐藏分类列（详情页可看），触控目标保持 44px |

**移动端实测（真实浏览器，非估算）**

- 320px：横向溢出 `0px`；375px：横向溢出 `0px`。
- 行高 78–146px（原先的「每字段一行」版本是 208px，已压缩）。
- 全部可点元素 ≥ 44px：筛选计数、筛选框、搜索框（44px）、行卡片、下载按钮。

**修掉的两个真实坑**

1. `.filter-row` 在窄屏改纵向 flex 后，搜索框的 `flex: 1 1 200px` 被解释成**高度**，撑出 130px 的空白块 → 窄屏改为 `flex: 0 0 auto`。
2. 详情页侧栏在窄屏仍是第二列，文字被压成竖排 → 详情布局改用 `grid-template-areas`，窄屏顺序为 标题 → 下载/数据 → 截图与安装步骤。

## 5. 详情页：下载与安装同屏

- 桌面：左列标题卡与正文卡拼成一张连续卡片，右列「下载」「数据」吸顶；**下载按钮与 4 步安装说明在同一屏内可见**。
- 移动：标题 → 下载面板 → 数据 → 截图 → 安装步骤。玩家先知道「这是哪个包、能不能下」，再往下读怎么装。
- 安装说明在主导航有独立入口，且每个详情页都带一套按 `layout` 字段区分的步骤（`separate-dir` 目录版、`separate-single` 单文件版）。
- 单独一块「常见错误」：放进 `resourcepacks/`、`mods/` 不生效；目录结构不一致；改完没刷新 —— 这三条对应 BRIEF 说的头号投诉。

## 6. 空状态与无结果状态（两个都要有）

| 场景 | 文案与去处 |
|---|---|
| 空状态：筛「可下载」为 0 条 | 「本站目前没有可直接下载的汉化包。我们正在按社区热度整理翻译任务清单，欢迎稍后再来。」—— 如实说明现状，而不是留一片空白 |
| 筛选无结果（关键词/加载器/版本组合为 0） | 「没有符合当前筛选条件的整合包。试试清除关键词或改选其他状态。」 |

两者共用容器但文案不同，避免「筛不出东西却不知道是数据没有还是关键词写错」。

## 7. 样式组织（CSS 架构师视角）

- 单一流向：`令牌 → 基础 → 布局 → 组件`，全部写在一个 `<style>` 里，组件只消费 `var(--*)`，不散写颜色与间距。
- 令牌：颜色（`--surface / --border / --text / --text-dim / --accent / 三状态色`）、间距（`--sp-1..7`）、圆角（`--radius*`）、字体栈。
- 低特异性：只用类选择器，没有 `!important`、没有 id 选择器参与样式、没有深层后代链（最多两层）。
- 布局：一维用 flex，二维（列表行、详情页）用 grid；行数据的响应式靠 `grid-template-areas` 与列数切换，而不是复制一套 DOM。
- 移动端与桌面端共用同一份 HTML：`.pack-meta` 在窄屏是 flex 容器，在 ≥1024px 用 `display: contents` 让子元素直接落到同一套栅格上。

---

## 8. 无障碍基线

- 语义化：`header/nav/main/section/aside/footer`、`h1–h3` 层级、列表用 `ul/li`。
- 键盘可达：行卡片 `tabindex="0"` + `role="button"`，Enter/Space 可打开详情；筛选计数是真正的 `<button>`，用 `aria-pressed` 表达选中态。
- 可见焦点：统一 `:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px }`。
- 对比度：正文 `#1a1a1a` / `#6b7280` 落在浅灰底上，AA 达标；状态不只靠颜色，文字始终存在。
- 屏幕阅读器：结果数与筛选结果用 `aria-live="polite"` 播报；行卡片带 `aria-label`（名称 + 状态 + 动作）。
- 图片：图标 `alt=""`（装饰性），CDN 截图加载失败时移除节点并给出「前往整合包页面查看」提示，不留空框。

## 9. 已知限制与下一步

- 截图与图标来自 CurseForge CDN，**本环境实测可加载**，但正式上线建议自建缓存，避免防盗链与慢加载。
- 详情页「提交翻译请求」只演示交互，文案明示「未接入后端」，真实实现需要事件落库 + 排队进度接口。
- 列表默认按下载量排序（作为需求热度的代理指标），这是**假设**：需要埋点验证「按下载量排序」是否等于玩家的关注顺序。
- 未做暗色模式：BRIEF 未要求，且当前令牌结构可以整体替换，后续加 `prefers-color-scheme` 只需覆盖令牌层。
