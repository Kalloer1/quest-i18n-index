## 0. 先说我最大的不认同

**这三个问题都不是瓶颈。** Q1 是选一份词典，Q2 是加一个 join，Q3 是加一个页面。
你们花了大量篇幅在这上面，但**项目的成败不取决于这三个问题的答案**。

真正没被讨论的是：**这个站靠什么留住人，以及谁来翻译。**

我把扫描数据摊开算了一遍（见 §2.1）：用业界通行的 10% 转化率估计，
**CF 前 500 的包全部完成探测，也就 1 万左右月访问量**——比一个中等 UP 主一期视频的引流还少。
在这个量级下，Q3（做汉化索引）能带来的流量增益，远大于「自己多翻 15 个包」。

我按问题的顺序回答，但结论集中在第 5 节。

## 1. Q1 / Q2 / Q3 逐个评

### Q1：术语库用现成的 `Dict-Mini.json`，还是自己扫 jar？

**同意「用现成的，但同时扫 jar」——但你们现在的理由说反了，所以要改的不只是决定，是理由。**

ADR-0005 自己已经用实测证明了：CFPA 是**覆盖层**不是术语表（create 只有 120 条 vs jar 的 3619 条），
而且**模组名只在 jar 里**（`itemGroup.*` 在 CFPA 中命中 0）。
`Dict-Mini.json` 的来源之一正是 CFPA，你们自己预期它缺 `Alex's Mobs`——这正是同一个缺口的症状。

⇒ 结论：**两个来源是互补的，不是二选一。** 引用 ADR-0005 的结论来否决「扫 jar」是自相矛盾的。
`Dict-Mini.json` 作为**起步种子**（零成本、有维护者、每周更新），jar 交叉校验作为**质量闸门**。

**你们低估的第二个问题：字典越大，消歧噪声越大。**
36,110/395,746（9%）是多候选。你们举的例子最能说明问题：

- `Create` → `["制造","创建","新建","制作","机械动力",...]`
- `Holystone` → `["圣石"]`

`Holystone` 这种**唯一译名**的高价值条目，根本不需要 39 万条的词典——39 万条反而制造假阳性
（合成词/普通词会误命中）。真正的价值来自**有界的那一份**：候选整合包的模组清单所对应的
`itemGroup.*` 与 jar 译名。**你们把一个有界问题（约 500 包 × 数百模组）解成了一个无界问题。**

**Q2 的答案不是「怎么选」，而是「能不能不选」：**

- `Create` → 整合包装了 `create` 模组 → 取「机械动力」。✅ 你们的方案在这里是对的。
- 但 `Create` 在任务文本里作普通动词「制造」时怎么办？你们的规则会**强制**取「机械动力」——这是错的。
- 正确做法：**模组名是一张封闭小表（几百条），单独成表、整词匹配、不参与通用消歧**；
  其余交给模型。把「模组名消歧」和「通用术语消歧」混在一个 39 万条词典里解决，是设计错误。

补一条具体机制：`Dict-Mini` 这类词典会同时收录**正确译名与常见错译**（它就是为「通用翻译器」准备的，
需要区分 `Piglin` 何时该音译、何时该保留）。**「取第一个」和「取模组命中的那个」都可能出错。**
这类词占比**不确定**，但足以说明多候选不是边角料问题。

**Q1 的第三个问题：9% 这个数字，不可信到能作为决策依据。**
39.5 万条这个量级让我怀疑包内混了**分页/别名/大小写变体**（**不确定**）。
如果真实多候选比例远低于 9%，Q2 的问题就没有你们以为的那么大；反之则更大。

**建议：动手前先做一次可证伪的实测（约 1 小时）**——拿 5 个候选包，
把 `Dict-Mini` 的候选列表与 jar 的 `itemGroup.*` 对撞，统计：
(a) 真·多候选比例；(b) 模组名表能覆盖多少；(c) 词典有但 jar 没有 / 反之 的比例。
**这三个数字出来之前，Q1 的取舍是猜的。**

**Q1 的第四个问题——你们没提的：许可传染。**
`i18n-Dict-Extender` 是**第三方仓库**，基于 CFPA 做「补差」。它自己声明的许可、来源与
署名要求，你们**没有核实**。ADR-0004 只核了 CFPA 与本仓库，没核这个衍生仓库。
既然整个项目建立在「接受 CC BY-NC-SA 并如实署名」之上，**这条必须补查**，不能默认继承。**（未核实，需查）**

### Q2：多候选怎么消歧？

见上。**方向对，机制错。** 正确形态不是「用整合包模组列表消歧一个 39 万条词典」，
而是**把模组名从词典里拆出来单独处理**。理由：

1. **模组名是封闭集合**（候选包涉及的全部模组，数百条量级），可以人工/半自动审校到接近 100% 准确。
2. **模组名不应参与通用消歧**：`Create` 到底是「机械动力」还是「创造」，取决于它指的是模组
   还是动词——这是**上下文判断**，不是词典查找。你们的规则只在「它是模组」这一支上正确。
3. **通用词典应当只用唯一/高置信条目**，其余降级为「提示给模型」而不是「强制替换」。
   强制替换是质量事故的主要来源。

### Q3：站上要不要同时列 VM / CFPA 已有的汉化？

**强烈同意，而且我认为这是你三个问题里唯一一个真正重要的——但它还不够。**

先说不够的地方：**「列出来」和「能用」是两回事。**
- 你们的约定表 #46 自己写了：「与别家汉化不能同时装」。那么一个「索引」如果不告诉玩家
  **装了本站的就不能装别家的**，就是在制造事故。
- 链接过去要标**状态**：VM 官网 58 个条目里 38 个 `stopped`、7 个 `translating`。
  把一个 2024 年停维的补丁作为「汉化在哪」的答案给玩家，等于没帮到他。
- 要标**版本绑定**（约定 #45）：VM 的 dawncraft 明确写「不支持最新版」。

**更重要的：如果索引是核心价值，那「自己做翻译」就不是必需品，而是可选的补充。**
这个推论你们没有往下走。它直接改变了项目的形态（见 §5）。

**反面意见（我必须说）：索引会稀释「本站产出」的信任度。**
如果页面上一半条目是别人的、一半是自己的，玩家无法判断该信谁，
而本站自己的产物在质量上**目前没有证据优于 VM / chiba233 / Kiwi233**（ADR-0003 自己也承认这一点）。
**解法是视觉上强分栏**：本站产出 vs 社区已有，两套完全不同的卡片形态，不要混排成一张表。

## 2. 最可能死在哪

### 2.1 风险一（最致命）：**需求规模不够，撑不起一个站**

你的文档里**没有算过 TAM**。我替你算了：

| 口径 | 数量 | 来源 |
|---|---:|---|
| CF 热度前 500 中「有任务书」 | 161 | `scan-cf500.tsv` 减掉 `none`(234)/`nodl`(85)/`toobig`(18) |
| 其中**可产出**（两种分离布局） | **57** | `separate-dir`(14) + `separate-single`(43) |
| 其中**已自带中文** | 14 | `newZh > 0` |
| **真实缺口（产出集合）** | **43** | |

CF 前十包的总下载量约 5,000 万 ~ 1 亿量级（**不确定**，我没实测这个数，只是量级判断）。
用业界宽松的 10% 下载→访问转化，**CF 前 500 全部覆盖 ≈ 1000 万下载 → 100 万访问**；
乘以「有任务书且无中文」的占比 **57/500 × 43/57 = 8.6%** → **约 8.6 万访问/月上限**。
但你们当前能覆盖的只有前 100（15 个缺口包），在这个口径下是**约 1 万/月**。

**1 万月访问**是什么量级？一个中等体量 MC UP 主的一期视频就能带来这个数。
**在这个流量下，任何「自建翻译流水线」的工程投入都收不回来**——不是收不回钱（本来就不商业化），
而是收不回**注意力**：没人用，就没有反馈，就无法迭代，质量就不会提升，就没人用。

**判断依据**：这是你们自己数据算出来的，不是我引入的外部假设。
唯一的反方论证是「冷门包玩家找不到汉化，痛点更强、忠诚度更高」——
**这可能是对的，但它同时意味着这个用户群更小、更难触达、更不活跃。**
冷门包的玩家本来就不来中文站。

### 2.2 风险二：**「不够好」+「不能共存」= 负价值**

约定 #46 说得很清楚：与别家汉化不能同时装，会互相覆盖。
所以本站的产物对玩家是一个**要么全用、要么不用的排他选择**。

那么玩家凭什么选本站而不是 VM / chiba233 / GTNH？
你们的产物是**只翻任务书，不翻模组手册（Patchouli）、不翻 KubeJS 魔改文本、不翻 FancyMenu、
不修硬编码文本**（后者需要 VaultPatcher / I18nUpdateMod 这类额外模组）。

**对玩家来说这是一道简单的算术题：装 VM 的一步到位，装本站的还要再装别家补模组空缺——
而两者不能共存。** 在这种情况下，本站的产物是**负价值**：它占用了玩家唯一能装汉化的那个位置，
却只填了一部分。

**这不是小细节，这是产品定义问题。** 你们的文档全程把「任务书翻译」当成一个自足的产品，
但从玩家视角，任务书只是整合包汉化的一部分，而且**它恰恰是最容易被单独替换的那部分**。
VM 的实测产物（`FTB-Skies-2-Chinese`）是 `kubejs/assets`(227) + `config/ftbquests`(39) +
`datapacks`(23) + `ftbteambases`(21) 的合集——任务书只占其中一小块。
**你们做的是那个大合集里的一小块，却要求玩家放弃整个合集。**

**判断依据**：`other-projects-2-community.md` §3.2 的实测 tree 与约定 #40/#42/#46。

### 2.3 风险三：**署名基础架在一个可能出问题的前提上**

`征询意见.md` 2.5 写：「`Dict-Mini.json` 已合并**模组官方仓库的译文**（正是 CFPA 缺的那块）」。
这句话是你们论证「用现成词典」的核心支柱，但 ADR-0004 的核实结果直接与它冲突：

> 模组自身 `zh_cn.json` 许可 **不透明**。`Creators-of-Create/Create` 在 GitHub 上是
> `NOASSERTION` / "Other"，根目录 `LICENSE` 返回 **404**。

⇒ **「模组官方仓库的译文」恰恰是你们自己查证过、认为许可不明的那一部分。**
把它从第三方仓库间接引入，并没有让许可变清楚，只是让链条变长了、更难追溯。

而你们要在这个基础上做 CC BY-NC-SA 4.0 的授权声明和署名。
**「我遵守了 CC BY-NC-SA」与「我的输出里混入了 404 许可的译文」同时成立——这是站不住的。**
ADR-0004 的后果栏已经写了「若将来要商业化，必须重做术语来源」，
但真正的问题不是商业化，是**非商业也不能用来源不明的数据再分发**。

**判断依据**：ADR-0004 §背景 表格第二行 vs `征询意见.md` §2.5。
**这两段在同一份项目里互相矛盾，值得先解决。**

（补充：ADR-0004 用「避开 CFPA 也换不来清白」来论证「不如直接接受 CC BY-NC-SA」——
这个论证在**修辞**上有力，在**法律**上无效。「A 不干净」不能推出「用 B 就干净」。
如果两条来源都不干净，正确结论是**缩小用量**（只用有明确许可的部分），而不是**接受许可**。）

## 3. 你们完全没考虑的方向

### 3.1 不做「站」，做「**补丁**」——嵌进已有的翻译流程

这是我能想到的、**工作量降一个数量级**的路子。

VM 已经把翻译流程做完了：Paratranz 平台 + 两个 GitHub Actions（每天早晚自动同步）+
`FTBQuestLangSpliter`（按章节拆 SNBT）+ `translate-tools`（色码检查 + snbt⇄json 互转）+
`Template-Repo`（模板 + `modpackinfo.json` 标准）+ VMTU（客户端自动识别并激活资源包）。

**而它的缺口恰好是你们想做的事：VM 官网 58 个条目里，38 个 `stopped`、7 个 `translating`、只有 13 个 `maintaining`。
也就是说「有流程、有工具、有分发，但翻译人手不够、维护不过来」。**

⇒ **最快见效的路径可能不是自建第 N 个汉化站，而是给 VM 提 PR / 认领 stopped 的包。**
理由：
- 玩家已经在 VM 那里了（有分发渠道、有 VMTU 自动激活、有社区认知）。
- 你们不用做站、不用做安装说明、不用解决「与别家不能共存」的冲突（因为这本来就是一家）。
- 你们不用从零建术语库和校验器——已经有了。

**这跟你们的目标不冲突**：如果目标是「让玩家玩到中文任务书」，这是最短路径；
如果目标是「做一个网站」，那这条不成立。**但你们的文档从头到尾没区分这两者——这是我要指出的元问题。**

### 3.2 发布**上游 PR**，而不是下游补丁

你们实测发现：`FTB-Skies-2-Aero`、`StoneBlock-4`、`OceanBlock-2`、`Tensura-Neo` 都是 **en 1 / zh 1**
——整本任务书只有一个语言文件条目，且已自带中文。

**含义**：FTB 自家包的译文是**上游收**的。既然 ATM / FTB 系列都「自己就带社区中文并随包分发」（你们 §2.4 的实测），
那么正确动作是**向上游提交 PR**，而不是做覆盖补丁。

**收益**：不产生「版本强绑定、与别家冲突、需要玩家手动装、需要双端装」的补丁；
玩家**什么都不用做**。这消灭了你们 §2.7 里 41/45/46 三条约定带来的全部摩擦。

**我应该诚实说明不确定性**：FTB 各整合包自己的仓库是否接受外部语言 PR、PR 流程是什么，**我没有核实**。
但这条路径值得在动手写站之前花一小时查清，因为它可能让整个「站」变得不必要。

### 3.3 目标用户可能是**服务端，不是玩家**

约定 #41 是全部约定里最锋利的一条：**服务端也必须装汉化补丁，否则进不去游戏。**

这意味着：**决定装不装汉化的人，往往是服主，不是玩家。** 服主是一次决策、影响几十到几百人。

你们的信息架构（BRIEF 里的列表页/详情页/安装说明）完全是面向玩家的。
但如果真实决策者是服主，那么「安装说明」不应该是**一个页面**，而应该是
**一个可复制的命令 / 一个脚本 / 一个 docker layer / 一份权威的版本对应表**。

**这条如果不做，你们在解决「玩家想装但没权限装」这个假问题。**

## 4. 「只做译文分离、不做内嵌」这个决定

**这个决定是对的，但你们的理由说轻了，而且有一个反面代价你们没算。**

### 4.1 为什么是对的（比你们说的更强）

你们的理由主要是「内嵌要改写玩家文件、解析出错会损坏玩家配置」。这个理由成立，但不够锋利。
**更锋利的理由是：内嵌布局的产物在玩家侧是「覆盖」，在版本兼容上是「强绑定」。**
约定 #45/#46 已经说了必须强绑定、不能共存。**三种布局里，只有内嵌布局的产物是「一次性快照」**——
上游整合包一更新章节，玩家装了本站内嵌补丁就会**丢失上游的新任务**（因为整个 `chapters/*.snbt` 被覆盖了）。

这一点你们在 §2.7 提到 #46「会互相覆盖」，但没说透：**内嵌产物不只与别家汉化冲突，
还与上游整合包自己的更新冲突。** 这是比「解析出错」严重得多的问题——
解析出错可以修，覆盖上游更新是**静默的数据丢失**。

⇒ **所以我不只同意，我认为这个决定应该被强化为一条硬规则**：
内嵌布局不是「暂不支持」，而应该是「**除非拿到上游整合包的翻译接口，否则永不支持**」。

### 4.2 反面代价（你们没算的）

**28 个（CF 前 100）内嵌包被排除，你们把它当成了「集合变小」这个数字代价。**
但真正的代价是**内容量**：

内嵌包里有一批**任务量极大、玩家基数极大**的包——
`deceasedcraft`、`mc-eternal-2`、`terrafirmagreg-modern`、`all-the-mods-9`、
`integrated-minecraft`、`society-sunlit-valley`、`darkrpg`、`craft-to-exile-2`、
`ftb-stoneblock-3`、`ftb-presents-architects-exodus`……

**这份名单里有不少是「玩家很多、任务书很长、且现在还是英文」的包**——
也就是说，**你们排除掉的很可能恰好是价值最高的一批**（不只是数量 28 vs 22 的问题）。
CF 前 500 的实测里 `embedded` 有 104 个，是 `separate-*` 合计 57 个的近两倍。

**这不改变结论（仍然不该做内嵌），但改变策略含义**：
这意味着「只做分离」的市场份额可能只有内嵌的三分之一。
如果 §2.1 的 TAM 问题成立，这个决定会把已经不大的市场再切掉 2/3。
**两条风险是叠加的，不是独立的。**

### 4.3 一个中间道路（你们没考虑）

内嵌布局**不是只能整体覆盖**。FTB Quests 的译文本质是 `key → value`，
键是 `quest.<十六进制ID>.title` 这类稳定标识。理论上可以：

1. 读内嵌的 `chapters/*.snbt`，**只抽取并翻译**文本值；
2. 产出**基于 ID 的映射表**，而不是重写整个文件；
3. 用 FTB Quests 自己的 lang 机制（若有）或一个轻量运行时注入。

**我不确定这条路在当前 FTB Quests 版本上是否可行**（需要查 FTBQ 源码里内嵌布局对应的版本
是否读 lang 目录——你们 research 里已确认 `26.1.2.1` 起才切分、`2100.1.0` 起才有独立 lang）。
**如果不可行，那就维持现决定；但如果可行，它把 28 个包从「不可做」变成「可做」。**
**建议花 2 小时核实，这是本次评估里 ROI 最高的一次核实。**

## 5. 更小的、能先验证价值的版本

**有，而且我认为你们应该做的是一个完全不同的东西。**

### 5.1 核心判断：**「索引」是价值，「翻译」是风险**

你们 Q3 的直觉是对的，但没有推到尽头。推到尽头就是：

> **先做「整合包任务书汉化索引」，一个字都不翻。**
> 然后在索引的基础上，**只翻那些索引证明有真实需求的包**。

### 5.2 MVP 的具体形态

**产物**：一个**静态 JSON 数据集 + 一个静态页**，没有后端，没有翻译流水线。

**功能只有三件**：
1. **查**：输入整合包名 → 看到它的任务书状态（可下载 / 自带中文 / 待翻译 / 内嵌不可做）+
   汉化在哪（VM / CFPA / 个人仓库的链接 + **状态** + **适用的整合包版本**）。
2. **装**：针对每一家汉化，给出**该家的**准确安装步骤（客户端 + 服务端），并明确**不能混装**。
3. **求**：一个「我想玩这个包但没有中文」的按钮。

**明确不做**：翻译、术语库、消歧、校验器、SNBT 解析、产出流水线。**全部不做。**

### 5.3 为什么这个 MVP 是对的

| 维度 | 现计划 | MVP |
|---|---|---|
| 需要的技术 | zip 探测 + SNBT 解析 + 术语库 + 消歧 + 翻译 + 校验 + 产出 + 站 | **只需要扫描**（已有）+ 一个静态页 |
| 上游依赖 | 词典许可、模组许可、CFPA 署名 | **零许可问题**（只做链接，不重分发任何内容） |
| 死法 | §2.2 的「不够好+不能共存」 | 不存在——你不替代任何人，只做导航 |
| 能验证什么 | 假设玩家要「本站的译文」 | **验证「玩家要的是信息」还是「要的是产物」** |
| 失败成本 | 数周工程 + 术语库维护 | 一个周末 |

**最关键的一点**：即使本站一个字都不翻，**§2.1 的 TAM 问题依然存在**——
索引站的流量上限和自己翻译站的流量上限是同一个（都是「有多少人在找整合包汉化」）。
**所以 MVP 的价值不只是省钱，而是用最低成本买到「这个需求到底有多大」的答案。**

如果索引站上线两个月没有任何流量，你得到了一个极有价值的结论：
**这个需求不存在，不该做这个项目。** 这个结论值一个周末。
而现计划会在花掉数周之后，仍然拿到同一个结论——只是更贵。

### 5.4 如果索引验证了需求，下一步做什么

**不要接着做翻译。** 按 ROI 排序：

1. **先给 VM 提 PR**（§3.1）——分发、工具、玩家全都有，你只出译文本体。
2. **再给上游提 PR**（§3.2）——让玩家什么都不用装。
3. **最后才是自建站**——只有当 1 和 2 都被证明走不通（比如 VM 不接受外部贡献、上游不接收 PR），
   自建站才有意义。**而到那时，你会有一份「哪些包真的有人要」的实测清单，
   而不是现在这份「哪些包在 CF 上热度高」的代理指标。**

## 6. 三个问题的最终回答

| 问题 | 我的回答 |
|---|---|
| Q1 用现成词典还是扫 jar | **都要**，但理由要改：两者互补而非替代（ADR-0005 自己已证明）。且**模组名单独成表**，不混入通用词典。**先补查 `i18n-Dict-Extender` 的许可**，再动手。 |
| Q2 多候选怎么消歧 | **方向对、机制错**。「模组名表消歧」只对「它是模组」这一支成立，对普通词义会强制误译。模组名（封闭、可审校）与通用术语（开放、只应提示不该强制）**必须分开处理**。 |
| Q3 要不要列别家汉化 | **要，且这是三问里唯一真正重要的**。但必须带**状态 + 适用版本 + 不能混装**的警告，否则是害人。**且它的推论比你们想的大得多：索引是核心，自建翻译是可选项。** |

## 7. 我不确定的地方（如实列出）

1. **CF 前十包的真实总下载量**——§2.1 的 TAM 估算用了量级判断，不是实测。**这是本文最弱的一环，但结论方向不太可能因它反转。**
2. **`Dict-Mini.json` 9% 多候选**是否被分页/别名污染——**未验证**，但会显著改变 Q2 的规模。
3. **内嵌布局能否用 ID 映射绕过全文件覆盖**（§4.3）——需要查 FTBQ 源码，**未核实**，ROI 最高。
4. **`i18n-Dict-Extender` 的许可与署名要求**——**未核实**，且与 ADR-0004 直接冲突。
5. **FTB 各整合包上游是否接受语言 PR**（§3.2）——**未核实**。
6. **`Dict-Mini` 里模组官方译文的比例**——决定 §2.3 的风险有多大，**未核实**。

## 8. 一句话总结

**你们把一个「分发与信息」问题，当成了「翻译工程」问题来做。**
技术研究很扎实（zip Range、三代布局、实测分布都是真功夫），
但**三个纠结的问题都是战术层面的，缺的是一个战略层面的自问**：

> **如果 VM 汉化组分发渠道、工具链、玩家认知全都有，只是缺人手——
> 我们为什么要在旁边再建一个站，而不是去给他们补人手？**
