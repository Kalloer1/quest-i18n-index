# 0006. 目标是「做一个网站」；先核实三件事，再以「索引 MVP」起步

日期：2026-10-17
状态：已接受

## 背景

引入了一位独立批判者（Claude Code）对项目做对抗性评审，其核心意见是：

> 你们把一个「分发与信息」问题当成了「翻译工程」问题。
> 如果 VM 汉化组分发渠道、工具链、玩家认知全都有、只是缺人手，
> 我们为什么要在旁边再建一个站，而不是去给他们补人手？

它同时指出三个实质问题，已逐条核实（结论见下）：

| 批判者的意见 | 核实结果 |
|---|---|
| 项目目标没被区分：是「让玩家玩到中文」还是「做一个站」 | **成立**。此前从未明确问过。已由用户明确：**要做站** |
| 全文没算过 TAM | **成立**。已补算，见 §代价 |
| `i18n-Dict-Extender` 许可未核实，与 ADR-0004 冲突 | **冲突属实，但结论是有利的**：实测其许可为 **MIT**，比 CFPA 的 CC BY-NC-SA 更宽松 |
| 「CF 前十下载量」是量级判断，是最弱一环 | **实测 1.21 亿**，比批判者估的「5千万~1亿」高 1.5~2 倍 |

## 决策

1. **项目目标是「做一个网站」**（而非仅「让玩家玩到中文任务书」）。
   作为副产品，若上游愿意接收译文，也应向上游提交——但**不以替代建站为目的**。
2. **动手写站之前，先花半天核实三件事**（见下），因为它们会让计划规模差一倍。
3. **核实之后以「索引 MVP」起步**：先做「整合包任务书汉化索引」，一个字都不翻；
   在索引证明有真实需求之后，再决定是否上翻译流水线。

## 要核实的三件事

| # | 问题 | 为什么关键 |
|---|---|---|
| ① | FTB 各整合包上游是否接收外部语言 PR？ | 若接收，则「提 PR」路径可消灭版本绑定与冲突（约定 #45/#46）等全部摩擦 |
| ② | 内嵌布局能否用「基于 ID 的映射」绕过整文件覆盖？ | 若能，被排除的 104 个内嵌包（CF 前 500）从「不可做」变「可做」；这是本次 ROI 最高的核实 |
| ③ | `Dict-Mini.json` 的 9% 多候选是否被分页/别名/大小写变体污染？ | 决定「多候选消歧」到底是边角料问题还是核心问题 |

## 「索引 MVP」的范围（明确不做什么）

**只做三件事**：

1. **查**：输入整合包名 → 看到任务书状态（可下载 / 自带中文 / 待翻译 / 内嵌不可做）+
   汉化在哪（VM / CFPA / 个人仓库的链接 + 状态 + 适用版本）
2. **装**：针对每一家汉化，给出**该家的**准确安装步骤（客户端 + 服务端），并明确**不能混装**
3. **求**：一个「我想玩这个包但没有中文」的按钮

**明确不做**：翻译、术语库、消歧、校验器、SNBT 解析、产出流水线。**全部不做。**

## 理由

- **「不能共存」使本站产物对玩家是一道排他选择**（约定 #46：与别家汉化不能同时装）。
  而 VM 的产物是合集（实测 `FTB-Skies-2-Chinese`：`kubejs/assets` 227 + `ftbquests` 39 +
  `datapacks` 23 + `ftbteambases` 21），本站只做其中任务书一小块。
  ⇒ 在**别人已覆盖的包上**，本站产物价值更低；只有在**无人覆盖的包上**才有优势。
- **索引无许可风险**：只放链接、不重分发任何内容，绕开词典/模组/CFPA 三重许可问题。
- **索引与翻译站的流量上限相同**（都是「有多少人在找整合包汉化」）。
  所以索引 MVP 不只是省钱，而是**用最低成本买到「这个需求是否存在」的答案**。
  两个月没流量 → 得到「不该做」这个结论，而这个结论值一个周末；
  按原计划则要花掉数周才能拿到同一个结论。

## 后果

- 索引必须带**状态**（VM 官网 58 条里 38 个 `stopped`，把停维补丁当答案等于没帮忙）、
  **适用整合包版本**（约定 #45：强绑定）、**不能混装警告**（约定 #46）。
- 索引中「本站产出」与「社区已有」必须**视觉上强分栏**，不能混排成一张表——
  否则玩家无法判断该信谁，而本站产物目前**没有证据**在质量上优于 VM / chiba233 / Kiwi233。
- 批判者「去给 VM 补人手」的建议**不被采纳为替代方案**，理由：
  VM 官网 58 条中 **38 个 stopped、仅 13 个 maintaining**，这是志愿者依赖型项目的衰竭曲线。
  其 backlog 不是「缺人手」，而是「人手模式不可持续」。
  自动化流水线是同一问题的**另一种解法**，且可能是唯一可规模化的那个。
- 批判者的「内嵌只占 1/3 市场 ⇒ 该放宽内嵌限制」推论**不被采纳**：
  内嵌产物覆盖 `chapters/*.snbt` 会**静默抹掉上游整合包的新任务**，
  这比「解析出错」严重得多（解析错可修，静默数据丢失不可逆）。
